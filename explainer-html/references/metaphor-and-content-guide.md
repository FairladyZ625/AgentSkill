# 比喻选题与内容纪律（explainer-html 必读参考）

## 1. METAPHOR 模式比喻选题五步法（必做，禁止跳过）

- **禁止默认开餐馆/上菜/后厨**：餐厅只是可选世界之一，不是默认模板。
- **整篇必须统一在一个比喻世界**：每个技术概念出场时先给比喻，真实技术名词紧跟在括号内（如「勘探样本（`Fact`）」）。
- **动笔前先从机制本身生发比喻世界**，在 HTML 顶部注释写明 `比喻世界: … / 为何贴切: …`，逐条回答以下 5 个发散点：
  1. **谁在动**：机制里有哪几个主体？谁求谁、谁卡谁、谁是中转？（角色关系 → 人际结构）
  2. **在哪儿动**：动作发生在什么样的空间？单一通道还是多点？层层关卡还是前厅/后场？（空间 → 地形）
  3. **靠什么流转**：凭据、票据、印章、钥匙、台账、回执……什么东西在传递、核对、或会丢失？（流转物件 → 道具）
  4. **错了长什么样**：出错时，现实里哪种事故和它同构？——走错门、记成烂账、搭错线、漏了检？（故障形态往往是最锐利的选题线索）
  5. **一句话向家人怎么说**：只用日常词向家人解释时，不自觉冒出的那个生活场景就是最佳候选。
- **换轨自检（交付前必做）**：把全文比喻词替换成中性词，如果机制依然只是干瘪装饰，说明在套模板；如果比喻与技术机制严丝合缝同构，则合格。

## 2. 内容纪律（两种模式通用，比风格更重要）

### ① 任务对照表是硬骨架，比喻是皮（2026-08-19 裁定）
- 凡汇报涉及北极星 / milestone / 多任务交付，页面必须有一张**直白的任务对照表**：
  - 每个 task 一行：task 名（人话）+ 干了什么（技术直述，**表内禁止比喻词**）+ 验证环境与实测证据 + 状态（`done` / `active` / `planned`）+ 锚点（PR 号 / commit / task id）。
  - 测试与验证状态直接列清单（哪些场景在什么环境跑过、哪些没跑），不许只给比喻性的「水质检验通过」。

### ② 写给没看过过程的人（2026-08-20 裁定）
- **第一句话就是结论**：不要先铺背景再揭晓；先说结果或发现，再给支撑细节。
- **自造词不许直接上页面**：「族」「lane」「净读数」等内部简写，第一次出现时必须用一整句话解释，或换成日常说法。
- **写完整句子**：禁止正文全靠箭头链（`A → B → C`）或连字符堆叠的速记短语。
- **提到文件、提交、参数、命令，每一个都配一句白话说明它是干什么的**。
- **分清「测到的」和「推出来的」**：数字要说明是实测还是估算；估算要说明计算方法与误差方向。

## 3. 落点与交付纪律

- **禁止调用外部托管画廊（如 Claude Artifacts publish）**：产物一律落盘到本地文件。
- **落点选择**：
  1. 属于某个在账 task 的汇报 → `harness/tasks/<task-dir>/artifacts/`
  2. 属于某个 decision 的解释材料 → `harness/decisions/decision-dec_<id>/`
  3. 属于研究 pack 的解释页 → 对应 research 目录内
  4. 无在账任务归属的探索性/全局汇报 → `tmp/orch/<主题>/index.html`
- **交付动作链**：
  1. 从 `templates/` 拷贝对应模式模板并写入内容
  2. 运行校验器：`node ~/.claude/skills/explainer-html/scripts/validate-explainer.mjs <file.html>`（红了就地修，直到全绿）
  3. 执行 `open <file.html>` 在浏览器打开，并在回复中给出可点击的本地文件链接。
